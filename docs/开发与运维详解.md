## 1. goctl 与代码生成

### 工具版本

| 工具 | 版本 | 说明 |
|------|------|------|
| go-zero | **v1.10.3** | 运行时 |
| goctl | **v1.10.2** | 代码生成器 |
| protoc | 36.2（本机验证） | |
| protoc-gen-go | v1.35.1 | |
| protoc-gen-go-grpc | 1.5.1 | |

**注意 goctl 与 go-zero 版本号不一致**，这是正常的：goctl 已从 go-zero 主模块拆分成独立 module `github.com/zeromicro/go-zero/tools/goctl`，最新是 v1.10.2，**不存在 v1.10.3**。v1.10.3 的 go-zero 模块里已经没有 `tools/` 目录了。

所以 Makefile 里 `GOCTL_VERSION` 和 `GO_ZERO_VERSION` 是两个独立的变量。

### 为什么生成物是手写的

`internal/handler`、`internal/logic`、`internal/types`、`internal/handler/routes.go` **都是手写维护的**，不是 goctl 直出。

原因：本机 goctl 版本可能与 `GOCTL_VERSION` 不一致，生成的样板会有差异；而且 goctl 会**覆盖**已有文件，直接跑一次就把手工改动冲掉了。所以：

```bash
make gen    # 生成到 .gen/，供人工比对合并
```

它**不会**碰 `internal/` 下的任何文件。这是刻意的保护。

### 生成产物与手写产物的一致性

这么做的代价是要手工保证 `.api` 契约与 Go 代码同步。约定：

- 改了 `api/desc/xxx.api` → 必须同步改 `internal/types/`（结构体）、`internal/handler/`、`internal/logic/`、`internal/handler/routes.go`
- `.api` 文件是**契约真源**，代码与它不一致时以 `.api` 为准

将来若验证 goctl 输出稳定，可以把 `make gen` 改成直接生成 + 用 `.in` 文件恢复手写逻辑，见 [templates/README.md](../templates/README.md)。**当前未启用。**

### 更新 proto

`api/desc/hello.proto` 是唯一允许存在的 proto，且**只用于自证**。更新方式：

```bash
protoc --proto_path=api/desc \
  --go_out=. --go_opt=module=charon \
  --go-grpc_out=. --go-grpc_opt=module=charon \
  api/desc/hello.proto
```

**不要**跑 `goctl rpc --zrpc_out`，它生成的 `cmd/rpc` 样板与本项目的拦截器约定不一致，会覆盖掉手工挂载的 `grpcx` 拦截器。

## 2. 配置加载

### 加载流程

```
cmd/api/main.go
  conf.MustLoad(*configFile, &c, conf.UseEnv())
    → 读 etc/charon-api.yaml
    → 用 os.ExpandEnv 展开 $VAR
    → 按 json tag 映射到 internal/config.Config
```

go-zero 用**结构体字段的 `json` tag** 决定配置文件的键名。这就是为什么 `internal/config/config.go` 里每个字段都带 `json:"..."` —— 不带 tag 的字段无法从配置赋值。

### 内嵌的框架配置

```go
type Config struct {
	rest.RestConf        // Host / Port / Timeout / MaxBytes / Log / Telemetry / Middlewares ...
	Auth   auth.Config
	Health HealthConfig
	DB     DBConfig
}
```

`rest.RestConf` 提供所有 HTTP 相关配置，**不要自己重复定义同名字段**，否则会覆盖掉框架默认值（比如自己写个 `Port int` 会让 go-zero 的端口默认值失效）。

### 默认值与校验

go-zero 的 tag 支持：

```go
MaxOpenConns int           `json:",default=20"`
Driver       string        `json:",default=pgx,options=pgx|postgres"`
DataSource   string        `json:",optional"`
PageSize     int           `json:"pageSize,optional,default=20,range=[1:100]"`
```

`options=` 和 `range=` 会在加载时校验，不合法直接启动失败——这是好事，配置错误早暴露。

> **注意**：本仓库的 `.golangci.yml` 若开启了 `staticcheck` 的 SA5008，会对 `json:",default=x,options=a|b"` 这种写法报「malformed json tag」。这是**误报**——go-zero 的 tag 不是标准 `encoding/json` 语法，而是它自己的约定。已在配置中排除该检查项。运行时行为由 go-zero 的 mapping 包负责，已实测正常。

### 环境变量约定

配置里用 `$VAR` 引用环境变量：

```yaml
DB:
  DataSource: $DB_DATA_SOURCE
```

这样密码不进仓库。`.env` 里的值需要被加载进环境——`docker compose` 会自动读 `.env`，本地直接跑则需要自己 export（或 `dev-up.ps1` 会处理）。

### 鉴权模式的校验

`Auth.Mode` 在启动期显式校验：

```go
if err := c.Auth.Validate(); err != nil {
	panic(fmt.Sprintf("Auth 配置非法: %v", err))
}
```

`pkg/auth.Middleware` 内部对非法值也做了**默认拒绝**处理（而不是默认放行）——不允许出现「配置写错 = 不鉴权」这种情况。

## 3. Trace 与日志

### 两套 trace 并存

| | 载体 | 用途 | 是否需要后端 |
|---|------|------|--------------|
| go-zero 自带 | W3C `traceparent` | otel span 采样上报，画调用链拓扑图 | 需要 OTLP collector |
| 本项目 `pkg/trace` | `X-Trace-Id` | 业务日志串联，排障时定位单次请求 | **不需要** |

**为什么自己造一套？** 因为 go-zero 的中间件只认 `traceparent`，不认 `X-Trace-Id`，而本地开发通常没有 OTLP 后端。如果日志串联依赖 otel，那本地就完全追不了请求。自造一套让**业务日志的可用性不依赖 otel 是否开启**。

两者不冲突：`traceparent` 照常透传，otel 开着就上报，关着也不影响业务日志。

### trace id 的流转

```
入站 X-Trace-Id（客户端带的）
   │
   ├─ sanitize()      ← 过滤非法字符、截断 64 字符
   │
   ├─ 为空 → NewID()  ← 16 字节随机 hex
   │
   ├─ 放进 context（trace.WithTraceID）
   ├─ 写回响应头 X-Trace-Id
   │
   ├─ logger.WithTrace(ctx) → 注入日志字段 traceId
   │
   └─ 出站：grpcx.UnaryClientTraceInterceptor 放进 gRPC metadata
              → 下游 UnaryServerTraceInterceptor 取出 → 继续串
```

### 为什么要 sanitize

`X-Trace-Id` 是**客户端可控**的，会被写进日志和响应头。不处理的话可以：

- 塞 `\r\n` 伪造日志行（日志注入）
- 塞超长字符串撑爆日志
- 塞响应头分隔符做头注入

所以 `sanitize` 只保留 `[A-Za-z0-9-_.]`，截断到 64 字符。全非法时退化为生成新 id（而不是用空串）。

### 404 / 405 的 trace id

**这里有个坑**：go-zero 的 `WithNotFoundHandler` 和 `WithNotAllowedHandler` 在**中间件链之外**被调用：

- 404：`engine.notFoundHandler` 自己组一条只含 trace/log 的链
- 405：直接交给 `router.SetNotAllowedHandler`，完全不经过链

也就是说 `server.Use(trace.Middleware)` **覆盖不到**它们。而「用户报接口 404」恰恰是最需要 trace id 的场景。

解法是手工包一层：

```go
rest.WithNotFoundHandler(trace.Handler(http.HandlerFunc(notFoundHandler)))
```

`trace.Handler`（`http.Handler` 版）就是为此存在，与 `trace.Middleware`（`rest.Middleware` 版）共用同一份逻辑。

### 日志字段注入

```go
ctx = logger.WithTrace(ctx)
logx.WithContext(ctx).Infof("...")   // 输出里带 traceId
```

必须显式调用，因为 go-zero 的 `WithContext` 只从 otel span 取 trace id，拿不到我们的 context key。

### 日志级别策略

`pkg/response` 里对错误日志做了分级：

```go
if biz.HTTPStatus() >= http.StatusInternalServerError {
	logx.WithContext(ctx).Errorf(...)
}
```

只有 5xx 打 error。**4xx 不打**——否则客户端传错参数就能把日志刷满，真出故障时反而看不见。

## 4. 鉴权

### 三种模式

| 模式 | 行为 | 适用 |
|------|------|------|
| `none` | 放行 | 本地开发 |
| `require` | 校验 `Authorization: Bearer <非空>` | 临时过渡 |
| `sdk` | 放行 + 打警告 | 预留给 sdk-auth |

### `require` 的能力边界（重要）

**它只检查 Bearer token 非空，不验签、不解析、不校验有效期。** 任何字符串都能通过，包括 `Bearer x`。

它的作用只是：

1. 拦住没有凭证的探测流量
2. 为将来换成真鉴权留好中间件挂载位置

因此有一条硬性约束：

> **`Auth.Mode=require` 期间，该服务禁止暴露到公网 Ingress。** 只能经集群内网访问。

这不是可以商量的建议。当前配置下任何人构造一个 `Authorization: Bearer anything` 就能访问全部业务接口。

### 替换成真鉴权

`sdk-auth` 合入后：

1. `pkg/auth.Middleware` 的 `ModeSDK` 分支里接上 sdk-auth 的校验器
2. 配置改 `Auth.Mode=sdk`
3. 此时才考虑开放 Ingress

`ModeSDK` 分支当前会打一条 `logx.Error` 警告，这是刻意的：配置了 `sdk` 却得到「不鉴权」的行为，如果没有日志会非常危险。

### 默认拒绝

`Middleware` 的 `default` 分支返回 403 而不是放行。虽然 `Validate()` 会在启动期拦住非法值，但多一层保险——**不允许「配置错误 = 不鉴权」**。

## 5. Health 探针

### 两个探针的分工

| 路径 | 类型 | 检查什么 | 失败后果 |
|------|------|----------|----------|
| `/health` | liveness | 什么都不检查 | **容器被重启** |
| `/readyz` | readiness | ping 数据库 | 从负载均衡摘除，不重启 |

### 为什么 liveness 不检查依赖

这是本文最值得记住的一条。

如果 liveness 也去检查数据库，那么数据库抖动 → 所有实例 liveness 失败 → kubelet 重启所有实例 → 数据库压力更大（所有实例同时重连）→ 雪崩加剧。

**重启解决不了依赖故障。** 依赖检查属于 readiness 的职责。

### 探针为什么不走鉴权中间件

如果探针被鉴权挡住，kubelet 拿不到 200 就会判定实例不健康——即使业务其实完全正常。一个鉴权配置错误会导致**全实例被摘除/重启**。

所以探针路由是单独注册的，不加任何中间件：

```go
for _, route := range health.Routes(healthConf, svcCtx.DBReady) {
	server.AddRoutes([]rest.Route{route})   // 没有 WithMiddlewares
}
```

注意这里**不能**用 `server.Use(auth.Middleware(...))` —— `server.Use` 是全局的，会把探针一起挡住。详见 [第 8 节](#8-中间件挂载范围)。

### 响应格式

探针**不用**业务统一外壳（`pkg/response.Body`）：

```json
{"status":"ok"}
```

原因是探针的消费者是 kubelet / LB 这类基础设施，不该依赖业务的响应约定。改一次业务格式就让所有探针失联是不可接受的。

### 探针保护

`Health.RequireToken=true` 时探针需要带 `X-Health-Token` 头，用 constant-time 比较避免通过响应耗时猜 token。

默认关闭的取舍：k8s 的 `httpGet` 探针来自 kubelet，来源可判定；且 `/health` 只暴露「进程存活」这一位信息。如果探针路径被暴露到不可信网络，再打开。

## 6. 数据访问层

### 分层职责

```
logic  →  repo  →  model  →  sqlx  →  pgx  →  PostgreSQL
```

| 层 | 只做 | 明确不做 |
|----|------|----------|
| `model` | 表结构（`db` tag） | 查询、业务规则 |
| `repo` | 拼 SQL、读写 | 业务判断、翻译错误码 |
| `logic` | 业务规则、错误翻译 | 拼 SQL、碰 HTTP |

### repo 为什么不翻译错误码

`repo.FindOne` 查不到时返回原始的 `sql.ErrNoRows`，**不**返回 `CodeNotFound`。

因为 `repo` 不该知道对外契约。将来如果产品决定「查不到返回空对象而不是 404」，只需要改 `logic`，一行业务无关的 SQL 都不用动。

翻译发生在 logic：

```go
item, err := repo.FindOne(l.ctx, req.ID)
if err != nil {
	if errors.Is(err, sql.ErrNoRows) {
		return nil, bizerr.NewFromContext(l.ctx, bizerr.CodeNotFound, err)
	}
	return nil, bizerr.NewFromContext(l.ctx, bizerr.CodeInternal, err)
}
```

### 为什么用 RETURNING 而不是 LastInsertId

```sql
INSERT INTO demo_item (name) VALUES ($1) RETURNING id
```

PostgreSQL 的 `database/sql` 驱动不保证支持 `LastInsertId`；`RETURNING` 是 PG 原生做法且只需一次往返。测试里用 sqlmock 断言了这条 SQL（`TestInsertUsesReturningID`），防止有人改回去。

### 连接池参数必须显式设置

```go
rawDB.SetMaxOpenConns(c.DB.MaxOpenConns)   // 关键的这条
rawDB.SetMaxIdleConns(c.DB.MaxIdleConns)
rawDB.SetConnMaxLifetime(c.DB.MaxLifetime)
```

`database/sql` 的 `MaxOpenConns` **默认是 0 = 无上限**。不设的话流量突增会把数据库连接打满。go-zero 的 `sqlx` 不代设这些，需要自己来。

`MaxLifetime` 设上限是为了让连接定期重建——否则可能一直用一个已被中间件（云上 PgBouncer 之类）单方面掐断的死连接。

### 启动期 Ping

```go
pingCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
if err := rawDB.PingContext(pingCtx); err != nil {
	logx.Must(fmt.Errorf("数据库无法连接，启动中止（不做内存回退）: %w", err))
}
```

在启动期就暴露连通性问题，让编排系统立刻看到启动失败并停下部署，而不是把一个「起来了但每个请求都 500」的实例放进负载均衡。

### 无 Memory 回退

**没有「连不上就换内存实现」的兜底。** 理由：

配置错误若被兜底掩盖，会在生产上表现成「服务健康、探针正常、但数据全是空的」。这种故障的排查成本远高于启动失败。

`DataSource` 留空是唯一合法的「不用数据库」表达方式，此时相关接口返回 503 且启动日志有明确提示。

## 7. Kubernetes 部署

清单在 [../deploy/k8s/](../deploy/k8s/)，是**待评审的起始模板**，不是可以直接上生产的最终形态。

### 要点

1. **探针**：api 用 `httpGet` 指向 `/health`（liveness）和 `/readyz`（readiness）；rpc 用 gRPC 健康检查（`RpcServerConf.Health=true` 已开启）。
2. **密钥**：`DB_DATA_SOURCE` 必须来自 `Secret`（`secretKeyRef`），不能写进 ConfigMap。
3. **网络**：`Auth.Mode=require` 期间 Service 必须是 `ClusterIP`，**不得**挂公网 Ingress。
4. **资源**：有 requests/limits。`MaxOpenConns` 应该与副本数一起算——N 个副本 × MaxOpenConns 不能超过数据库的连接上限。
5. **时区**：镜像里装了 `tzdata`，因为日志时间戳和业务时间依赖它。

### 副本数与连接数

容易忽略的算术：

```
总连接数 = 副本数 × DB.MaxOpenConns
```

这个值必须小于数据库的 `max_connections`（还要给运维留余量）。扩容前先算这笔账，否则扩副本反而会把数据库打死。

## 8. 中间件挂载范围

**这是本脚手架里最容易踩的坑，单独一节。**

### go-zero 的两种挂载方式

| 方式 | 作用范围 | 注意 |
|------|----------|------|
| `server.Use(mw)` | **所有路由**，含探针和 404 处理 | 全局，无法排除某个路由 |
| `rest.WithMiddlewares([]Middleware{...}, routes...)` | 只有列出的路由 | 需要手工分组 |

**go-zero 不会对同一个路由去重中间件**（`engine.bindRoute` 里的 `ng.middlewares` 是一个简单累加的列表）。所以两种方式混用会导致某个路由上中间件执行两次。

### 本项目的分组

```
全局（server.Use）
  └─ trace.Middleware          ← 所有路由都要，包括探针（探针也要能串日志）

业务路由（rest.WithMiddlewares）
  └─ auth.Middleware           ← 只包业务路由

探针路由（单独 AddRoutes）
  └─ 无中间件                   ← 刻意不鉴权，见第 5 节
```

### 为什么 trace 全局挂而 auth 按组挂

- trace **应该**作用于探针：探针请求也要能串日志。
- auth **不应该**作用于探针：否则鉴权配置问题会让 kubelet 误判实例不健康。

因为 `server.Use` 无法按路由排除，所以 auth 只能用 `WithMiddlewares` 手工包业务路由组。

### 顺序

`WithMiddlewares` 传入的中间件按**传入顺序由外到内**包裹，所以：

```go
[]rest.Middleware{auth.Middleware(...)}   // 只有 auth 一个
```

trace 在最外层（因为它是全局的，会先执行）。这样鉴权失败时也能拿到 trace id 排障。

### 如果要加新中间件

先想清楚作用范围：

- 所有路由都要 → `server.Use`
- 只有业务要 → 加进 `routes.go` 的 `WithMiddlewares` 列表
- 只有探针要 → 一般不需要

**不要**为了省事把 auth 挪到 `server.Use`——那会让探针返回 401，k8s 会判定实例不健康。

## 9. FAQ / 踩坑记录

### `go mod tidy` 后 zrpc 相关依赖报 missing go.sum entry

`internal/config` 引入了 `zrpc`，而 zrpc 会拖进 etcd / k8s client 等一大堆依赖。跑 `go mod tidy` 即可，首次会比较慢。若私有 GOPROXY 拉不到，改用公共源：

```bash
GOPROXY=https://goproxy.cn,direct go mod tidy
```

### staticcheck 报 `malformed json tag`

见 [第 2 节](#2-配置加载)的说明——是误报，因为 go-zero 的 tag 语法不是标准 `encoding/json`。

### 全项目构建慢

主要是 zrpc 的依赖树（etcd + k8s client）。`cmd/api` 其实不直接需要 zrpc，但 `internal/config` 里的 `RpcConfig` 引入了它。如果这个成本不可接受，可以把 `RpcConfig` 拆到单独包，让 api 的依赖树瘦下来。当前为了配置集中管理，先接受这个成本。

### 端口 8080 被占用

8080 是 `q-bot` 的（见仓库根目录 `docker-compose.yml`）。charon api 用 **8888**，别改回去。

### `make` 在 PowerShell 里报语法错误

Makefile 用了 `$$`、`test -f`、`rm -rf` 等 POSIX 写法。用 Git Bash / WSL，或用 `scripts/dev-up.ps1`。

### `postgres:18-alpine` 拉不到

```bash
POSTGRES_VERSION=17-alpine make dev
```

（本项目环境无法访问镜像仓库，未能实际验证 `postgres:18-alpine` 这个 tag 是否存在。若拉取失败直接降 17。）

### gRPC 反射在生产暴露了方法签名

`cmd/rpc/main.go` 里只在 `dev` / `test` 模式注册反射：

```go
if c.Mode == service.DevMode || c.Mode == service.TestMode {
	reflection.Register(grpcServer)
}
```

生产环境务必 `Mode: pro`，否则所有方法签名对外可见。

### gRPC 新建连接没有超时

`grpc.NewClient` 是**惰性连接**，不提供拨号超时参数（`WithBlock`/`WithTimeout` 对它无效）。超时必须逐调用用 context 控制：

```go
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()
resp, err := client.Say(ctx, req)
```

`grpcx.NewClient` 因此**不接受** timeout 参数——不在签名上暗示一个并不存在的保证。
