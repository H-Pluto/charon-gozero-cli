# 本地启动

三种场景，按你的情况选一种：

- [A. 标准本地](#a-标准本地docker-起-postgres) —— 有 Docker，最省事，推荐
- [B. 不用数据库](#b-不用数据库) —— 只想跑通 HTTP 链路，不装任何东西
- [C. 云库隧道](#c-云库隧道跳板机) —— 要连云端开发库

---

## A. 标准本地（Docker 起 Postgres）

### 一次性的准备

```bash
make tools     # 装 goctl / protoc 插件 / migrate
make init      # 生成 .env + 下载依赖
```

需要本机已有 `protoc`。Windows 上 Makefile 要用 **Git Bash 或 WSL** 执行。

### 启动

```bash
make dev
```

这个目标做了四件事：

1. `docker compose up -d postgres` 起数据库
2. 轮询 `pg_isready` 等数据库真的能接受查询（不是只看端口通）
3. `make migrate` 应用迁移
4. `goreman start` 用 [Procfile](../Procfile) 同时拉起 api 和 rpc

看到 `Routes:` 列表就说明起来了。api 在 `8888`，rpc 在 `9090`。

### 验证

```bash
# 自证接口（响应里 traceId 应该是你传进去的那个）
curl -i -H "X-Trace-Id: demo-trace" "http://127.0.0.1:8888/api/v1/hello?name=charon"

# 探针
curl "http://127.0.0.1:8888/health"     # 存活，永远 200
curl "http://127.0.0.1:8888/readyz"     # 就绪，会真的 ping 数据库

# 数据库链路（这条能成才说明整条链路通了）
curl -X POST "http://127.0.0.1:8888/api/v1/demo" \
     -H "Content-Type: application/json" \
     -d '{"name":"first"}'
curl "http://127.0.0.1:8888/api/v1/demo"
curl "http://127.0.0.1:8888/api/v1/demo/1"
curl -X DELETE "http://127.0.0.1:8888/api/v1/demo/1"
```

### 只跑 api

```bash
make run
```

前提是数据库已经在跑且 `DB_DATA_SOURCE` 能连上。

### Windows

```powershell
powershell -File scripts\dev-up.ps1
```

加 `-Migrate` 会额外跑迁移。这个脚本是为纯 PowerShell 环境准备的——Makefile 里的命令需要 POSIX shell。

## B. 不用数据库

只想验证 HTTP 链路（路由、中间件、响应格式、鉴权）时，不用装任何东西。

**做法**：让 `DB.DataSource` 为空。默认配置里它是 `$DB_DATA_SOURCE`，所以只要不设这个环境变量、且 `.env` 里也不设，它就是空的。

```bash
# 确保没有污染的环境变量
unset DB_DATA_SOURCE
./output/charon-api -f etc/charon-api.yaml
```

**预期行为**：

| 请求 | 结果 |
|------|------|
| `GET /api/v1/hello` | 200 正常 |
| `GET /health` | 200 |
| `GET /readyz` | 200（DB 未配置视为就绪） |
| `GET /api/v1/demo` | **503**，`{"code":501}` |

启动日志里会有一条明确提示：

```
未配置 DB.DataSource：数据库相关接口将不可用（返回 503）。
```

这不是错误，是有意留的口子。注意与「配了但连不上」区分——那种情况会**启动失败**，见下。

## C. 云库隧道（跳板机）

要连云端开发库，走 SSH 隧道而不是从笔记本直连。原因和步骤见 [../scripts/cloud/README.md](../scripts/cloud/README.md)。

核心就是把云端 Postgres 端口转发到本地：

```bash
ssh -N -L 15432:<云端库地址>:5432 <跳板机用户>@<跳板机>
```

然后指向隧道端点：

```bash
export DB_DATA_SOURCE="postgres://<用户>:<密码>@127.0.0.1:15432/charon?sslmode=disable"
make run
```

注意端口用 `15432` 之类的非默认值，避免和本地 Postgres 的 `5432` 撞上。

## 常见问题

### 启动报 `bind: Only one usage of each socket address`

端口被占。多半是上一次的进程没退干净：

```bash
taskkill //F //IM charon-api.exe     # Windows
pkill -f charon-api                   # Linux / Git Bash
```

### 启动直接 fatal，报 `failed to connect to ...`

**这是设计行为**：配了 `DB.DataSource` 就会真连，连不上就启动失败，不回退到内存实现。原因见 [README 第 7 节](../README.md#7-数据库)。

排查顺序：

1. 数据库在跑吗？`docker compose ps`
2. 主机名对吗？**容器内要用服务名 `postgres`，不能用 `127.0.0.1`**
3. 库建了吗？`charon` 这个库要存在
4. 真不需要数据库就把 `DataSource` 留空，见场景 B

### `/api/v1/demo` 返回 501

该实例没配数据库。配好并跑 `make migrate` 即可。

### `postgres:18-alpine` 拉不下来

```bash
POSTGRES_VERSION=17-alpine make dev
```

### `readyz` 返回 503

数据库连不上了（但进程还活着）。响应体里有原因：

```bash
curl "http://127.0.0.1:8888/readyz"
{"status":"unavailable","error":"..."}
```

这时 `/health` 应该仍然返回 200 —— 这是有意的：依赖故障时不该让编排系统重启容器，重启解决不了依赖问题。

### 日志里没有 traceId

确认两件事：入口调了 `logger.WithTrace(ctx)`，且用的是 `logx.WithContext(ctx)` 而不是 `logx.Info`。

### 想开鉴权试试

编辑 `etc/charon-api.yaml`：

```yaml
Auth:
  Mode: require
```

然后：

```bash
curl -i "http://127.0.0.1:8888/api/v1/hello"                        # 401
curl -i -H "Authorization: Bearer anything" "http://127.0.0.1:8888/api/v1/hello"  # 200
curl -i "http://127.0.0.1:8888/health"                              # 200，探针不受影响
```

`require` 只校验 Bearer 非空、**不验签**，所以 `Bearer anything` 也能过。这是临时门闩，此模式下禁止公网 Ingress，详见 [README 架构约束](../README.md#9-架构约束)。

### 想验证 gRPC

```bash
go run ./cmd/rpc -f etc/charon-rpc.yaml
```

`dev` 模式下开了 gRPC 反射，所以有 `grpcurl` 的话可以直接调：

```bash
grpcurl -plaintext -d '{"name":"charon"}' 127.0.0.1:9090 hello.Hello/Say
```

没装 grpcurl 也可以跑集成测试，它用内存内连接测同一条链路：

```bash
go test ./internal/svcerpc/ -v
```

**生产环境记得关掉反射**（`etc/charon-rpc.yaml` 里 `Mode` 改成 `pro`），否则所有方法签名都会暴露出去。
